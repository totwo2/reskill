# 需求清单（requirement-brief.md）· N0.2 蒸馏产物模板

> **本文件是什么**：N0.2 节点（聊天记录 → 需求清单）的标准化产物。
> 它是审计代理（J4 / N0.5）判定的**唯一真源**——审计只读这份，不读聊天全量。
> 也是 N1 签字时与事实表（fact-sheet.md）**同批签、必须对得上**的两张纸之一。
>
> **存放与引用**：本文件是权威模板，放在 `skills/reskill/prompts/requirement-brief.md`。
> 编排层（主 agent）在发布项目时把它复制到该项目的 `.publish-staging/requirement-brief.md`，
> 从当前会话蒸馏填充后使用。`auditor.md` 的 `{{REQUIREMENT_BRIEF}}` 指向填充后的这个文件。
>
> **为什么要有这一关**：聊天里混着「已采纳的需求」「被推翻的念头」「模型的附和」。
> 直接喂给审计 = 把废案当需求，审计会拿「CLI 没实现」去判一个早被否决的 CLI。
> 蒸馏 = 只留老高原话支撑的、带否决区的干净判据。

---

## 一、蒸馏的三条硬规则（填之前先读）

| 规则 | 内容 | 违反后果 |
|---|---|---|
| **原话原则** | 每条需求必须附**老高原话**（blockquote `>`）。AI 归纳的、没原话支撑的，不许进 R2 | 审计失去锚点，判据无效 |
| **否决区必填** | R4「已否决」不许为空。空着 = 没仔细翻聊天，审计会拿废案当需求 | N0.2 准出被脚本拒（`rejected_section_nonempty=false`） |
| **人工确认** | R5 跟 N1 事实表**一起签字**（同一批，签字时两张纸对一眼），不新增介入点 | 两张纸对不上没人发现 |

> 为什么跟事实表一起签：它们是同一件事的两面——事实表说「这东西对外是什么」，
> 需求清单说「这东西本来要做什么」。分两次签 = 两张纸可能对不上。

## 二、模板（复制后填充 `{{...}}`）

```markdown
# 需求清单（审计判据唯一真源）

> 来源：{{SESSION_DATE}} 会话。以下每条必须附老高原话；**没有原话的条目不许写**。
> 被推翻的念头另列「已否决」区（R4），审计不得引用。

## R1 一句话要什么
> 老高原话：「{{R1_QUOTE}}」

## R2 必须做到
| # | 需求 | 老高原话 | 出处 |
|---|---|---|---|
| 1 | {{R2_1_REQ}} | 「{{R2_1_QUOTE}}」 | {{R2_1_SRC}} |
| 2 | {{R2_2_REQ}} | 「{{R2_2_QUOTE}}」 | {{R2_2_SRC}} |
| … | … | … | … |

## R3 明确不要（禁区）
| # | 不要什么 | 老高原话 |
|---|---|---|
| 1 | {{R3_1}} | 「{{R3_1_QUOTE}}」 |
| 2 | {{R3_2}} | 「{{R3_2_QUOTE}}」 |
| … | … | … |

## R4 已否决（审计禁止据此判定）
- 「{{R4_1}}」——提出过，**未采纳**，不算需求
- 「{{R4_2}}」——……
（本区必须非空；空着 N0.2 准出不过）

## R5 老高对这份清单的确认
signed_by: 老高
confirmed_at: ____
```

## 三、填写纪律（审计代理会据此核）

1. **R1** 是定位句，不是功能列表。一句话说清「这是要做什么方向的东西」。
2. **R2** 是「必须做到」的逐条需求，每条带原话 + 出处（哪次会话/哪句话）。
   - 审计代理会拿 R2 逐条去源码找锚点（表 A 覆盖表）。
   - 审计发现的「必要超纲（🟢）」会回写补登记进 R2——那时也要补原话或标「老高确认必要」。
3. **R3** 是禁区。凡写进 R3 的，事实表（fact-sheet.md）的「禁用词」必须能对应上（见第四节）。
4. **R4** 是已否决区。**必须非空**。列的是「提过但没采纳」的念头，审计不得据此判「未实现」。
5. **R5** 是签字块。与 N1 事实表同批签；签之前必须做第四节的联动校验。

---

## 四、与 fact-sheet.md 的联动校验（N1 签字前置，两条纸对不上 → 拒绝签字）

> **规则**：老高在 R5 签字前，必须确认本清单与 N1 事实表（`.publish-staging/fact-sheet.md`）对得上。
> 对不上 = 两张纸描述的是两件事 → **拒绝签字**，先改哪边由交付方定（改需求 or 改事实表）。
> 机器可辅助，但最终是人眼；脚本只负责**把对不上的地方亮出来**，不代替人判。

### 4.1 逐条对应表（签字时逐项打勾）

| 本清单 | 事实表对应字段 | 一致性要求 | 打勾 |
|---|---|---|---|
| R1 一句话要什么 | 事实表「一句话定位」 | 语义一致，不互相矛盾 | ☐ |
| R2 每条必须做到 | 事实表「能力 / 功能清单」 | 每条 R2 在事实表有对应事实，不漏 | ☐ |
| R3 每条明确不要 | 事实表「禁用词」 | 每条 R3 在禁用词有登记，不漏 | ☐ |
| R4 已否决 | 事实表「能力 / 功能清单」 | R4 任何一条**不得**作为功能被卖出 | ☐ |

### 4.2 机器辅助

填充完两份文件后，跑：

```bash
python3 scripts/verify_brief_factsheet.py \
  --brief .publish-staging/requirement-brief.md \
  --factsheet .publish-staging/fact-sheet.md
```

脚本会：

- **结构校验（机器可靠，对应 N0.2 准出）**：R1–R5 齐全 / R4 非空 / 至少 1 处老高原话 blockquote / R5 签字块存在。
  对应 `.publish-state.json` 的 `N0.2.evidence.has_quotes` 与 `rejected_section_nonempty`。
- **联动校验（启发式，仅亮红灯/黄灯，交人定）**：
  - 🔴 **硬矛盾**：R3/R4 条目原话作为「能力」出现在事实表能力清单里 → 清清楚楚「说了不要却写成功能」→ **拒绝签字**，先消矛盾。
  - 🟡 **覆盖缺口**：某条 R2 在事实表能力清单找不到对应 → 黄灯，人确认是漏写还是确实没做。
  - 🟡 **禁区未登记**：某条 R3 在事实表「禁用词」找不到对应 → 黄灯，人确认禁区是否漏登。
  - 🟡 **否决泄漏**：某条 R4 出现在事实表能力描述里 → 黄灯，人确认是不是当成功能卖了。

> 脚本对「硬矛盾」才 exit 1（拦签字）；其余一律 🟡 + exit 0，交人眼。
> 设计原则：查不出的结论报「需人工确认」，**绝不替人判「你错了」**（诬告比不查更糟）。

## 五、编排层收尾（主 agent 做，你不用做）

1. 把填充后的本文件落到 `.publish-staging/requirement-brief.md`。
2. 跑 `verify_brief_factsheet.py --brief ... --factsheet ...`：
   - 结构不过（无 R4 / 无原话）→ N0.2 准出不过，停在 N0.2，不进 N0.5。
   - 出现 🔴 硬矛盾 → 提示老高「两张纸对不上，拒绝签字」，退回改需求或改事实表。
3. N0.2 通过 → 把 `has_quotes` / `rejected_section_nonempty` 写进 `.publish-state.json` 的 N0.2 节点。
4. 拉起 N0.5 审计代理时，把本文件绝对路径填进 `auditor.md` 的 `{{REQUIREMENT_BRIEF}}`。
